# 迎战结算架构决策与 POC 验收门

状态：生产入口已接入7张迎战牌；完整原生契约及真实多人尚未验收。2026-11-01。
此文覆盖旧方案中“API 全覆盖”和“意图拆解等价”的过强表述。

## 当前生产路径与边界

B04、C04、C10、C11、U28、U35、R09都在牌效顺序内等待同一`Core/EngageCmd`。
机会在第一个等待前预占，按战斗、轮次与敌实例由全队共享；真实动作沿用敌人原目标，
吸收与完成收益只归发起者。通过原生异步动作体的初次入口确认动作开始，不能以Task返回
代替。意图演出不计入吸收；轮次变化、切侧、Reset和换战斗使旧窗口失效。
后续跳过仅作用正常敌方阶段，不拦截玩家阶段其他模块的`TakeTurn`调用。

失败或第三方取消不会退款预占机会，因为不能证明其前缀未产生部分效果；未真正开始原生
动作时不发完成收益。规则仍不改写目标、意图数字或额外`RollMove`。本轮生产适配器的边界
回归与真实Harmony的合成方法验证分别记账，均不冒充原生敌人或双客户端验证。

当前存档采用原生房间入口检查点重建。中战斗sidecar快照、网络重连是否由原生动作重放
完整恢复，尚无双端证据；不新增未验证的同步协议，也不把单进程双玩家夹具写成联机支持。

## 历史原型已验证的有限范围（2026-10-31）

锁定 0.107.1，隔离存档、禁用 Steam、TestMode=false 的真实 headless 进程：在玩家阶段直接 await `MonsterModel.PerformMove()`；LEAF_SLIME_S 的 TACKLE_MOVE 实际吸收 3，玩家生命不变；同轮重复请求返回 performed=false、absorbed=0、completed=false；正常敌方阶段 `Creature.TakeTurn()` 前缀跳过已消费目标一次，其余敌人行动后进入下一轮。独立运行器核对这些精确结果，不仅相信驱动的 passed 字段。

`DamageBlockInternal` 的 decimal 返回值通过仅观察的 Harmony postfix 累计到 AsyncLocal 窗口；finally 恢复外层窗口。该统计尚未验证坚甲、多段、反击或嵌套窗口的归属。`PerformMove` 自身执行动作、推进 OnMovePerformed 并写战斗历史；候选实现不额外 RollMove。正常阶段的意图播放尚未跳过，须继续核验视觉和特殊动作。

上述历史`EngagePrototype`须显式设置 `VOLIBEAR_TEST_ENGAGE=1`并走隔离开发bootstrap；
当前`Core/EngageCmd`生产入口已随普通Mod初始化安装，两者不能混淆。历史测试仍缺卡牌内顺序、
完成响应、死亡/结束判断的完整原生验证、跨轮历史对照、召唤、存档恢复。测试退出资源泄漏导致
严格总报告失败，不应把场景通过解释为发布验收。

## 决策

保留现有迎战规则，不擅自降级。官方公开 API 尚未确认能直接在玩家出牌中驱动敌人行动；候选实现是自定义 EngageCmd/执行上下文，结合 Harmony 对内部动作执行入口和敌方调度器打补丁。PerformMove、MoveStateMachine 是调查线索，不是已验证的安全调用方案。必须针对 StS2 0.107.1 实际程序集核验签名、调用链和状态所有权。

不得从意图显示数值重建所谓“等价行动”：意图不是完整动作程序，不能覆盖隐藏状态、随机分支、阶段转换、附加状态、召唤等。眩晕也不天然等同于消耗本轮行动。任何语义降级必须由用户另行批准。

## 必须保持的结算契约

1. 卡牌先完成迎战前牌效，进入迎战窗口；后续牌效等待敌人真实动作完成。
2. 每敌每轮一次机会，全队共享；保留敌人原目标分配。已行动目标performed=false、吸收=0，不触发迎战后响应。进入执行前预占资格，防止重入重复行动；异常或取消不退款，避免部分动作重放。
3. 执行目标当前真实动作，逐段经过原伤害、格挡、触发和死亡管线；不能仅模拟攻击数值。
4. 吸收为本次迎战中发起者的格挡实际吸收伤害总量，不等于格挡净变化或消耗；不计队友的格挡，也不计意图演出期间的其他伤害。坚甲不消耗格挡但照计吸收；完全格挡、多段攻击均计入。需核验DamageResult字段真实含义，不能假定字段存在。
5. 动作实际开始、玩家存活且战斗继续才算完成；仅完成时发布一次 engageCompleted，按规则执行遗物/能力响应，再继续后续牌效。死亡/战斗终止不继续打伤害。
6. 多目标迎战按稳定顺序串行；窗口分别记录目标吸收并按卡牌规则汇总，过滤死亡/失效目标，不以全局 block 前后差求吸收。
7. 正常敌方阶段跳过已提前结算的动作，但不可重复或漏掉状态机推进、回合计数、状态持续时间及应发生的回合触发。推进由迎战还是原调度器负责，必须根据实际调用链确定唯一所有者。
8. 隐藏行动状态以战斗/轮次/敌实例为身份，战斗结束清理，明确中途存档支持。瞬时吸收不入存档。窗口用 try/finally 退出，不遗留标记。
9. v1 优先单人验证；联机必须单独验证同步事件、选择上下文、随机数及执行顺序，不能据单人通过宣称联机支持。

## 原型顺序与验收

先核验内部调用链并写出实际方法签名/补丁点，再做一张测试卡与一个简单敌人，最后扩展以下用例：

| 用例 | 验收要求 |
|---|---|
| 单段攻击 | 玩家回合中真实执行，格挡/扣血正确，卡牌后续正确 |
| 多段攻击、完全格挡 | 吸收逐段累加，触发次数与原流程一致 |
| 攻击附带状态/混合行动 | 副作用、随机与敌自身状态不丢失 |
| 非攻击动作 | 按既定迎战资格与领域规则处理，不凭显示数字替代 |
| 同敌重复迎战/重入 | 同轮不重复，不触发虚假的完成事件 |
| 坚甲 | 格挡不扣但吸收计入，溢出正常扣血 |
| 反击导致敌死、玩家死、战斗结束 | 正确中断，无悬挂等待/残留窗口 |
| 多目标与中途死亡/召唤 | 顺序稳定，无错计或重复目标 |
| 后续敌方阶段与下一轮 | 不重复行动、不跳错下一招、回合计数与状态持续时间正确 |
| 完成响应 | 遗物、U04/U19/R18等按既定触发条件/次数结算 |
| 存档/恢复与特殊阶段敌人 | 明确支持范围及失败用例，不隐瞒例外 |

每例保存前后状态、事件顺序和日志。至少测试原调度无补丁对照，确认不迎战时原行为不变。只有原型通过才能把迎战改为“可实现已验证”。简单敌人的单次成功不代表全怪物兼容。

## 与已有工作区关系
